# ហេត្តអ្វី? pi-web?

ខ្ញុំនិយាយបានថាខ្ញុំស្ទើរតែពូកែទៅវិញក្នុងការប្រើ Claude Code។ ខ្ញុំជារឿងតែងតែប្រើវា។ ប្រសិនបើខ្ញុំមិនអង្គុយមុខកុំព្យូទ័រទេ ខ្ញុំក៏ពិចារណាអំពីវាដែរ។ ខ្ញុំមានអារម្មណ៍ថាខ្ញុំមិនបានប្រើ tokens ច្រើនគ្រប់គ្រាន់ទេ។ នោះគឺជាថ្ងៃដំបូងនៃ Claude Code។ ហើយខ្ញុំបានគិតថា ហេតុអ្វីខ្ញុំមិនអាចបន្ត (resume) ពីទូរស័ព្ទរបស់ខ្ញុំបាន? ខ្ញុំបានដំឡើង Termius ប៉ុន្តែខ្ញុំមិនពេញចិត្តនោះទេ។

ខ្ញុំបានចាប់ផ្តើមបង្កើតរបស់ខ្ញុំខ្លួនឯង ប៉ុន្តែបញ្ឈប់បន្ទាប់ពី Claude បានដាក់ផ្សាយកម្មវិធីទូរស័ព្ទ Claude Code របស់ពួកគេ។

បន្ទាប់មកខ្ញុំបានជួបប្រទះបញ្ហា-disc រលួយ (herniated disc) ហើយខ្ញុំមិនអាចធ្វើអ្វីច្រើនទេ។ ពេលក្លាយត្រឡប់មកវិញ ខ្ញុំមានអារម្មណ៍ថាខ្ញុំរៀបរទ្របន្តិច ហើយខ្ញុំចង់បន្តគម្រោង Claude Code របស់ខ្ញុំតាម web/pwa វិញ។

បន្ទាប់មក Claude Code បានចាប់ផ្តើមហាមការប្រើប្រាស់ខាងក្រៅ harness ផ្ទាល់ខ្លួនរបស់ពួកគេ។ ហើយខ្ញុំមានអារម្មណ៍ថាវាមិនកម្រិតទេ។

បន្ទាប់មកខ្ញុំបានរកឃើញ pi.dev ហើយស្វែងយល់បន្តិច ប៉ុន្តែមិនបានចូលរួមពិតប្រាកដនោះទេ។ ខ្ញុំបានអានអំពីវា មើលវីដេអូអំពីវា ហើយសម្រេចចិត្តផ្តល់ពិសេសការពិសាជីវៈពេញលេញ ហើយឥឡូវនេះខ្ញុំពេញចិត្ត pi ពេញលេញ។

ដោយសារវាជា open source ខ្ញុំមានអារម្មណ៍ថាវាចាំបាច់សម្រាប់ការបង្កើត។ ខ្ញុំក៏ទទួលបានជម្រើស provider ផ្សេងៗផងដែរ។ ខ្ញុំក៏មានអារម្មណ៍ថាពឹងផ្អែកលើ provider/model តែមួយដូចជា Anthropic/Claude មិនមានភាពធន់បានទេ។

ដូច្នេះខ្ញុំកំពុងបង្កើតវានៅទីនេះ។

Checkout នេះត្រូវបានរក្សាទុកជាសក្តានុពល local-model របស់ pi-web។ វាតាមគោលនៃគម្រោង upstream សម្រាប់ការកែតម្រូវដែលចែករំលែក ខណៈដែលរក្សា deployment ក្នុងតំបន់, ភាពស្ថិតស្ថេរនៃ context, និងការធ្វើពិសោធន៍ local-model នៅលើ track ដោះស្រាយដែលផ្លាស់ប្តូរសិទ្ធិ។

## ហេតុអ្វី local model ត្រូវការ profile ដំណើរការផ្សេង

បទពិសោធន៍ដើមរបស់ pi-web គឺជាមូលដ្ឋានដ៏អស្ចារ្យ ប៉ុន្តែការស្ម័គ្រសំណល់ local មានរបៀបបរាជ័យផ្សេងពី model ដែលមាន hosting ជាធម្មតា។ Local model អាចបន្ថយល្បឿនខ្លាំងនៅពេល context រំភើប ចែករំលែក memory កំណត់ជាមួយផ្នែកផ្សេងទៀតនៃម៉ាស៊ីន ឈប់បន្ទាប់ពីផលិតការស្រាវជ្រាវតែប៉ុណ្ណោះ ឬបាត់បង់ការដំណើរការយូរដោយបរាជ័យ transport local បណ្តោះអាសន្ន។ ការសម្រេចករណីទាំងនេះដូចគ្នាទៅនឹងបរាជ័យ cloud ធ្វើឱ្យ UI មើលទៅមានភាពសមគរ ខណៈដែល session ពិតប្រាកដនៅតែភ្នែង។

សក្តានុពលនេះទស្សនៈផ្ទៃបញ្ហានេះជាជម្រាល៖

1. **រក្សា upstream ជាស្នូលជាទីប្រឹក្សា។** UI ដែលចែករំលែក និងគឺកិត្តិសក្តានុពលនៃ session បន្តមកពី pi-web; ការកែតម្រូវ local ត្រូវបានដាច់ខាងពី effective Local Mode។
2. **ការពារមុនពេលសង្គ្រោះ។** ព្រំដែន context 65% ដែលផ្អែកលើភាគរយត្រូវបានអនុវត្តមុនការហៅ model បន្ទាប់ រួមទាំងការហៅនៅក្នុង long tool loops។
3. **សង្គ្រោះតែប្រសិនបើមានភស្តុតាង។** ការបន្តដោយស្វ័យប្រវត្តិមានកំណត់ទៅក្នុង context, transport, និង thinking-only incidents ដែលកំណត់បាន—មិនមែន authentication, quota, ឬ provider errors ពេញប៉ុណ្ណោះ។
4. **កំណត់រាល់សកម្មភាពស្វ័យប្រវត្តិ។** Recovery incidents ត្រូវបាន deduplicate ចាំបាច់មាន progress មុនសង្គ្រោះមួយទៀត ហើយការដំណើរការ (startup) ពិចារណាតែ Local session ដ៏សកម្មថ្មីៗមួយប៉ុណ្ណោះ។
5. **រក្សាចេញដោយដៃ។** Force Compact សរុបជាជាងសម្អាត history ដូច្នេះ user អាចសង្គ្រោះ session ដោយមិនប្រហែលថា context មិនធ្លាប់មាន។
6. **ការពារភាពសមគរនៃ cloud។** Cloud Mode រក្សា semantics និង controls របស់ upstream; ការប្រសើរឡើងសម្រាប់ local-model មិនបានកំណត់វិញសម្រាប់ cloud sessions ដោយស្រលាញ់ទេ។

នេះជាខុសគ្នាពិតប្រាកដនៅក្នុង fork នេះ៖ វាសម្រេច local inference ជាបរិយាកាសដំណើរការដាច់ខាង មិនមែនត្រឹមតែឈ្មោះ model ផ្សេងទៀតក្នុង dropdown ទេ។
