# ဘာကြောင့် pi-web လဲ။

ကျွန်တော် Claude Code ကို အတော်လေး စွဲလမ်းနေပါတယ်။ အမြဲတမ်း သုံးနေပါတယ်။ ကွန်ပျူတာရှေ့မှာ မထိုင်တဲ့အချိန်ဆိုရင်တောင် အဲဒါအကြောင်း တွေးနေမိပါတယ်။ token တွေ လုံလုံလောက်လောက် မသုံးမိဘူးလို့ ခံစားရပါတယ်။ Claude Code ရဲ့ အစောပိုင်းကာလတွေပါ။ ကျွန်တော့်ဖုန်းကနေ ဘာလို့ ဆက်မလုပ်နိုင်ရမှာလဲလို့ တွေးနေခဲ့ပါတယ်။ Termius ကို သုံးကြည့်ခဲ့ပေမယ့် သိပ်မကြိုက်ခဲ့ပါဘူး။

ကိုယ်ပိုင်တစ်ခု စတင်ဖန်တီးခဲ့ပြီး Claude က သူတို့ရဲ့ Claude Code မိုဘိုင်းအက်ပ်ကို မိတ်ဆက်တဲ့အချိန်မှာ ရပ်လိုက်ခဲ့ပါတယ်။

အဲဒီနောက် ကျောရိုးအပြားထွက်တဲ့ ဝေဒနာရခဲ့ပြီး ဘာမှ တကယ်မလုပ်နိုင်ခဲ့ပါဘူး။ အချိန်တွေကြာသွားပြီး နည်းနည်း သက်သာလာတော့ Claude Code ကို web/pwa ကနေတစ်ဆင့် ဆက်လုပ်ချင်လာခဲ့ပါတယ်။

အဲဒီနောက် Claude Code က သူတို့ရဲ့ ကိုယ်ပိုင် harness အပြင်ဘက်မှာ သုံးတာကို စတင်ပိတ်ပင်လာပါတယ်။ ဒီတော့ တန်ဖိုးမရှိဘူးလို့ ခံစားရပါတယ်။

အဲဒီနောက် pi.dev ကို တွေ့ခဲ့ပြီး နည်းနည်းစူးစမ်းခဲ့ပေမယ့် တကယ်နက်နက်နဲနဲ မလေ့လာဖြစ်ခဲ့ပါဘူး။ အကြောင်းဖတ်တယ်၊ ဗီဒီယိုတွေကြည့်တယ်၊ ပြီးတော့ အပြည့်အဝ စမ်းကြည့်ဖို့ ဆုံးဖြတ်ခဲ့ပြီး အခုဆို pi ကို လုံးဝ စိတ်ဝင်စားနေပါပြီ။

Open source ဖြစ်တဲ့အတွက် တည်ဆောက်ရကျိုးနပ်တယ်လို့ ခံစားရပါတယ်။ Provider အမျိုးမျိုး ရွေးချယ်ခွင့်လည်း ရှိပါတယ်။ Anthropic/Claude လို provider/model တစ်ခုတည်းကိုပဲ မှီခိုနေတာက ရေရှည်မှာ မတည်တံ့နိုင်ဘူးလို့လည်း ခံစားရပါတယ်။

ဒါကြောင့် ဒီမှာ တည်ဆောက်နေပါတယ်။

## ဒေသတွင်းမော်ဒယ်တစ်ခုသည် ဘာကြောင့် ခွဲခြားထားသော လည်ပတ်ရေးပရိုဖိုင်တစ်ခု လိုအပ်သနည်း

မူလ pi-web အတွေ့အကြုံသည် အကောင်းဆုံးအခြေခံတစ်ခုဖြစ်သော်လည်း ဒေသတွင်း inference သည် ပုံမှန် host လုပ်ထားသော မော်ဒယ်များနှင့် ကွဲပြားသော ပျက်ကွက်မှုပုံစံများရှိသည်။ ဒေသတွင်းမော်ဒယ်တစ်ခုသည် context တိုးလာသည်နှင့်အမျှ အလွန်နှေးကွေးသွားနိုင်ပြီး၊ စက်၏ ကျန်အစိတ်အပိုင်းများနှင့် ကန့်သတ်ထားသော မှတ်ဉာဏ်ကို မျှဝေနိုင်ပြီး၊ အကြောင်းပြချက်ကိုသာ ထုတ်လုပ်ပြီးနောက် ရပ်တန့်သွားနိုင်ပြီး၊ ယာယီ ဒေသတွင်း transport ပျက်ကွက်မှုကြောင့် ရှည်လျားသော run တစ်ခုကို ဆုံးရှုံးသွားနိုင်သည်။ ထိုအခြေအနေများကို cloud ပျက်ကွက်မှုများအတိုင်း တိကျစွာ ကိုင်တွယ်ခြင်းသည် UI ကို ကိုက်ညီမှုရှိသကဲ့သို့ ထင်ရစေသော်လည်း အမှန်တကယ် session သည် အားနည်းဆဲဖြစ်သည်။

ဤထုတ်ဝေမှုသည် ပြဿနာကို အလွှာလိုက် ချဉ်းကပ်သည်-

1. **Upstream ကို ဦးစွာ ထိန်းသိမ်းပါ။** မျှဝေထားသော UI နှင့် session အပြုအမူများသည် pi-web မှ ဆက်လက်ရရှိနေပြီး၊ ဒေသတွင်းပြောင်းလဲမှုများကို ထိရောက်သော Local Mode နောက်တွင် သီးခြားထားသည်။
2. **ပြန်လည်ရယူမှုမတိုင်မီ တားဆီးပါ။** ရှည်လျားသော tool loop အတွင်းရှိ ခေါ်ဆိုမှုများအပါအဝင် နောက်ပိုင်း provider ခေါ်ဆိုမှုများမတိုင်မီ ရာခိုင်နှုန်းအခြေပြု 65% context နယ်နိမိတ်ကို အကောင်အထည်ဖော်သည်။
3. **သက်သေရှိမှသာ ပြန်လည်ရယူပါ။** အလိုအလျောက် ဆက်လက်လုပ်ဆောင်မှုကို အသိအမှတ်ပြုထားသော context, transport နှင့် thinking-only ဖြစ်ရပ်များသို့သာ ကန့်သတ်ပြီး၊ authentication, quota သို့မဟုတ် provider ၏ မတော်တဆ error များအတွက် မဟုတ်ပါ။
4. **အလိုအလျောက် လုပ်ဆောင်ချက်အားလုံးကို ကန့်သတ်ပါ။** ပြန်လည်ရယူမှု ဖြစ်ရပ်များကို ထပ်နေသောအရာများ ဖယ်ရှားပြီး၊ နောက်ထပ် ကယ်ဆယ်ရေးတစ်ခုမတိုင်မီ တိုးတက်မှု လိုအပ်ပြီး၊ startup သည် မကြာသေးမီက လုပ်ဆောင်နေသော Local session တစ်ခုကိုသာ အများဆုံး ထည့်သွင်းစဉ်းစားသည်။
5. **လက်ဖြင့် ထွက်ခွာမှုကို ထိန်းသိမ်းပါ။** Force Compact သည် သမိုင်းကို ဖျက်ပစ်ခြင်းအစား အကျဉ်းချုပ်ပြုလုပ်သဖြင့်၊ အသုံးပြုသူသည် context သည် ဘယ်တော့မှ မရှိခဲ့ဟု အတုယူခြင်းမပြုဘဲ session ကို ကယ်ဆယ်နိုင်သည်။
6. **Cloud ကိုက်ညီမှုကို ကာကွယ်ပါ။** Cloud Mode သည် upstream semantics နှင့် ထိန်းချုပ်မှုများကို ထိန်းသိမ်းပြီး၊ ဒေသတွင်းမော်ဒယ် optimization များသည် cloud session များကို တိတ်တဆိတ် ပြန်လည်သတ်မှတ်ခြင်း မပြုလုပ်ပါ။

ဤ fork တွင် အမှန်တကယ် ကွာခြားချက်မှာ- ဒေသတွင်း inference ကို dropdown တစ်ခုတွင် မော်ဒယ်အမည်တစ်ခုအဖြစ်သာ မဟုတ်ဘဲ ခွဲခြားထားသော လည်ပတ်ရေးပတ်ဝန်းကျင်တစ်ခုအဖြစ် ကိုင်တွယ်သည်။
