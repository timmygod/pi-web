# ဘာကြောင့် pi-web ဖြစ်သလဲ?

ကျွန်ုပ်က Claude Code ကို အရမ်းထိုလိုက်ပါတယ်။ ကျွန်ုပ်က အမြဲဖြစ်အောင် အသုံးပြုပါတယ်။ ကွန်ပျူတာရှေ့မှာ ထိုင်နေချိန်မဟုတ်ရင်ပဲ တွေးတောနေတာကလည်း ဒါပဲ ဖြစ်ပါတယ်။ Token များစွာ မသုံးလိုက်ဘူးလို့ ခံစားရပါတယ်။ အဲဒါကတော့ Claude Code ရဲ့ ရှေ့ပိုင်းကာလဖြစ်ပါတယ်။ ဖုန်းကနေ ဘယ်လို ပြန် ဆက်လုပ်နိုင်မလဲလို့ တွေးစမ်းခဲ့ပါတယ်။ Termius ကို setup လုပ်ခဲ့ပေမယ့် အရမ်း ကြိုက်ခဲ့ပါဘူး။

Claude ကတော့ သူ့ရဲ့ Claude Code mobile app ကို တင်လာတဲ့အခါ ကျွန်ုပ်က ကိုယ့်အတွက် ကိုယ်တည်ဆောက်ခဲ့တာ ကို ရပ်လိုက်ပါတယ်။

သားရေခေါင်းရောဂါ (herniated disc) ကြောင့် အသက်ဝင်လာပြီး အလုပ်အကိုင်လုပ်ဖို့ မရနိုင်တော့ပါဘူး။ ကြာလာပြီး အနည်းငယ် ပြန်လည်တော့ ပြန်ထလိုက်ပြီး ကိုယ့်ရဲ့ Claude Code ကို web/pwa project အနေနဲ့ ဆက်လုပ်ချင်တော့လာပါတယ်။

နောက်ပိုင်းမှာတော့ Claude Code က သူတို့ရဲ့ harness အပြင်မှာသုံးတာကို ပြုလွယ်တင်တော့ပါသည်။ တန်ဖိုးမရှိတော့ပါဘူးလို့ ခံစားရပါတယ်။

နောက်ဆုံးမှာ pi.dev ကို တွေ့ပြီး အနည်းငယ် စူးစမ်းကြည့်ခဲ့ပေမယ့် အတော်လေးနက်နက်စွာ ဝင်ရောက်ခဲ့တာ မဟုတ်ပါဘူး။ အကြောင်းအရာတွေ ဖတ်ရှုခဲ့ပြီး မြင်တွေ့ရှိချက်တွေ ကြည့်ခဲ့ပါတယ်။ ကျွန်ုပ်ကတော့ အပြည့်အဝ စမ်းရမယ်လို့ ဆုံးဖြတ်ခဲ့ပြီး ယခုကတော့ pi ကို နှစ်သက်လိမ့်ပါပြီ။

Open source ဖြစ်လို့ က่อတည်ဖို့တန်တယ်လို့ ခံစားရပါတယ်။ Provider selection choice များစွာ ရနိုင်တဲ့အတွက် ကြိုက်ပါတယ်။ Anthropic/Claude ဆိုတဲ့ provider/model တစ်ခုတည်းကို အကြောင်းပြုသည့်အတွက် မပေါ့ဆခဲ့ပါဘူး။

ဒါကြောင့် ကျွန်ုပ်က ဒီမှာ တည်ဆောက်ထားတာ ဖြစ်ပါတယ်။

ဒီ checkout ကတော့ local-model edition ဖြစ်တဲ့ pi-web ကို မှတ်တမ်းတင်ထားပါတယ်။ Shared improvements အတွက် အပေါ်ဘက်ရဲ့ project ကို လိုက်နာလျက် local deployment, context stability, local-model testing တွေကို ကွဲပြားခြားနားပြီး release track အဖြစ် ထားရှိထားပါတယ်။

## Local Model ကို ဘာကြောင့် ခွဲခြားစီမံပိုင်ခွင့် ပုံစံ ကွဲပြားစေရသလဲ

မူရင်း pi-web experience က အရမ်းတိကျတဲ့ အခြေခံချက် ဖြစ်ပေမယ့် local inference ကတော့ hosted model တစ်ခုရဲ့ failure mode ကို ခွဲခြားစွာ သုံးနှုန်းစနစ် ဖြစ်ပါတယ်။ Local model တစ်ခုက context ကြီးလာချိန်မှာ အားလုံး အနှေးဖြစ်လို့ အများအားဖြင့် ကြာပြီး၊ မှတ်ပုံတင်စနစ် ကို အခြား computer component တွေ နဲ့ ကြုံတက်နေပြီး၊ thinking ကိုပဲ ဖြစ်စေပြီး ကြာပြီး သွားအောင် ကြာပြီး၊ transient local transport failure ကြောင့် ပျက်တာလည်း ဖြစ်နိုင်ပါတယ်။ ဒီအခြေအနေတွေကို အတိအကျ cloud failures ကိုပဲ လုပ်တဲ့အခါ UI က compatible ဖြစ်ပေမယ့် session တစ်ခုကတော့ အသက်ခံနိုင်စွမ်းနည်းနေပါတယ်။

ဒီ edition ကတော့ အောက်ပါအတိုင်း layer များနဲ့ ဝင်ရောက်စီမံပါသည်:

1. **အပေါ်ဘက်ကို အဆိုက်ခံပါ။** Shared UI နဲ့ session behavior တွေကတော့ pi-web ကနေ ဆက်လက်လာပါတယ်။ Local changes တွေကတော့ effective Local Mode နောက်မှာ ကွဲပြားစွာ ထားရှိထားပါတယ်။
2. **ပြန်လည်ဖြည့်စွက်ပြီးအောက်မှာ ကာကွယ်ပါ။** Percentage-based 65% context boundary ကို next model calls များ အထွင်ရှင်း နှောင့်ယှက်ပြီး၊ ကြာတဲ့ tool loops ကာလအတွင်း calls များကိုပါ ကာကွယ်ပါတယ်။
3. **အထင်က တရားတည်းတင်စစ်ပြီး မတင်လိုက်ပါ။** Automatic continuation က recognized context, transport, thinking-only incidents တွေကိုပဲ ပြောင်းလဲနိုင်ပါတယ်—authentication, quota, provider errors တွေ မပါဝင်ပါဘူး။
4. **Autonomous action တိုင်းကို ပိုက်တွန်ပါ။** Recovery incidents တွေကို deduplicate လုပ်ပြီး၊ rescue တစ်ခုအတွင်း ရွေးချယ်စဉ်နီးစွာ ဖြစ်ပြီး၊ startup က အနောက်တစ်ခုမျှတရုံပဲ Local session ကို ထည့်သွင်းစဉ်ပါ။
5. **Manual exit ကို ထားခဲ့ပါ။** Force Compact က history ကို နှိမ့်ထားတာ မဟုတ်ဘဲ summary ပေးပါတယ်၊ ဒါကြောင့် user က context က မဖျက်ပါဘဲ session ကို ပြန်လည်ရှာဖွေနိုင်ပါတယ်။
6. **Cloud compatibility ကို ကာကွယ်ပါ။** Cloud Mode က အပေါ်ဘက်ရဲ့ semantics နှင့် controls များကို ဆက်လက်ထားရှိပါတယ်။ Local model optimizations တွေက silently cloud sessions တွေကို redefine မလုပ်ပါဘူး။

ဒါကတော့ ဒီ fork တွင်းမှ အမှန်တကယ် ကွဲပြားတဲ့အချက် ဖြစ်ပါတယ်။ Local inference ကို ထင်ရှားတဲ့ operational environment အဖြစ် များအားဖြင့် dropdown တစ်ခုထဲက model name အခြားတစ်ခုအဖြစ် မသုံးပါဘူး။
