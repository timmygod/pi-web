# 为什么选择 pi-web？

我有点沉迷于 Claude Code，总是离不开它。如果不坐在电脑前，我也会想着它。我觉得自己的 token 用得太少了。那是 Claude Code 的早期阶段，我一直在想：为什么不能从手机上恢复会话？我设置了 Termius，但并不太喜欢它。

于是我开始自己做一个，结果 Claude 推出了他们的 Claude Code 移动应用，我就停下了。

后来我得了椎间盘突出，真的什么都做不了。时间过去了，我感觉恢复了一些，于是想继续我的通过 Web/PWA 使用 Claude Code 的项目。

接着 Claude Code 开始禁止在其官方 harness 之外使用，我觉得不值得再折腾了。

然后我发现了 pi.dev，稍微探索了一下，但并没有深入。我读了一些关于它的文章，看了一些相关视频，决定全面尝试一下，现在我完全爱上了 pi。

因为它是开源的，我觉得值得为之构建。同时我也可以选择不同的 provider。我也觉得只依赖一个 provider/模型，比如 Anthropic/Claude，是不可持续的。

所以我正在这里构建它。

本 checkout 作为 pi-web 的本地模型版本进行维护。它跟随上游项目获取共享改进，同时将本地部署、上下文稳定性和本地模型测试保留在一条独立发布的轨道上。

## 为什么本地模型需要不同的运行配置

原始的 pi-web 体验是一个出色的基础，但本地推理与典型的托管模型有着不同的失败模式。本地模型可能在上下文增长时突然变慢，与机器上的其他部分共享有限的内存，在仅产生推理后就停止，或者因短暂的本地传输故障而丢失一次长时间运行。将这些情况完全当作云端故障来处理，会让 UI 看起来兼容，但实际会话仍然脆弱。

这个版本分层处理这个问题：

1. **优先保留上游。** 共享的 UI 与会话行为继续来自 pi-web；本地改动被隔离在有效的 Local Mode 之后。
2. **先预防，再恢复。** 在执行后续模型调用（包括长工具循环内的调用）之前，会强制执行基于百分比的 65% 上下文边界。
3. **仅在确凿证据下恢复。** 自动继续仅限于已识别的上下文、传输和仅思考（thinking-only）事件——而不包括认证、配额或任意 provider 错误。
4. **为每个自主行动设定边界。** 恢复事件会去重，下一次救援前必须有所进展，并且启动时最多考虑一个最近活跃的 Local 会话。
5. **保留手动退出。** Force Compact 会总结而非清空历史，因此用户可以拯救一个会话，而无需假装上下文从未存在过。
6. **保护云端兼容性。** Cloud Mode 保留上游的语义和控制；本地模型优化不会悄悄重新定义云端会话。

这正是这个 fork 的真正区别所在：它将本地推理视为一个独立的运行环境，而不仅仅是下拉菜单中的另一个模型名称。
