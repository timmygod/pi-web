# 为什么是 pi-web？

我有点沉迷于 Claude Code。我一直在用它。不坐在电脑前的时候，我就在想它。我感觉自己烧的 token 还不够多。那是 Claude Code 的早期阶段。我当时在想，为什么我不能从手机上继续呢？我配置了 Termius，但不太喜欢。

我开始自己做一个，但当 Claude 推出他们的 Claude Code 移动应用后，我就停下了。

然后我得了椎间盘突出，几乎什么也做不了。时间流逝，我感觉恢复了一些，想继续我的 Claude Code web/pwa 项目。

然后 Claude Code 开始禁止在其自有框架之外使用。我觉得这不值得了。

然后我发现了 pi.dev，稍微了解了一下，但还没有真正深入。我阅读了相关资料，看了视频，决定好好试一下，现在完全迷上了 pi。

因为它是开源的，我觉得值得为它构建。我还能选择不同的提供商。我也觉得只依赖一个提供商/模型（比如 Anthropic/Claude）是不可持续的。

所以我在这里构建它。

## 为什么本地模型需要不同的运行配置

原始的 pi-web 体验是一个出色的基础，但本地推理与典型的托管模型有不同的故障模式。本地模型可能会随着上下文的增长而急剧变慢，与机器的其他部分共享有限的内存，在仅产生推理后停止，或因短暂的本地传输故障而丢失长时间运行。将这些情况完全视为云故障会使 UI 看起来兼容，但实际会话仍然脆弱。

此版本分层解决问题：

1. **首先保留上游。** 共享的 UI 和会话行为继续来自 pi-web；本地更改隔离在有效的 Local Mode 之后。
2. **预防优于恢复。** 在后续模型调用（包括长工具循环中的调用）之前，强制执行基于百分比的 65% 上下文边界。
3. **仅凭证据恢复。** 自动续写仅限于已识别的上下文、传输和仅思考事件，而非身份验证、配额或任意提供商错误。
4. **限制每个自主操作。** 恢复事件会被去重，在另一次救援之前需要取得进展，并且启动时最多考虑一个最近活跃的 Local 会话。
5. **保留手动退出。** Force Compact 会总结而不是擦除历史记录，因此用户可以拯救会话，而无需假装上下文从未存在过。
6. **保护云兼容性。** Cloud Mode 保持上游语义和控制；本地模型优化不会静默地重新定义云会话。

这就是此分支的真正区别：它将本地推理视为一个独特的运行环境，而不仅仅是下拉菜单中的另一个模型名称。
